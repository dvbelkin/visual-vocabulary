# AGENTS.md

## Назначение проекта

Visual Vocabulary — двуязычный учебный сайт для студентов. Он помогает выбрать
тип визуализации по аналитической задаче, понять ограничения метода и изучить его
на небольшом интерактивном примере.

Целевой стек:

- Astro и TypeScript;
- Apache ECharts для всех интерактивных диаграмм;
- статическая сборка, пригодная для GitHub Pages;
- русский и английский языки с одинаковым объёмом контента;
- CSS с общими дизайн-токенами, без обязательного UI-фреймворка.

`PLAN.md` является источником правды о порядке миграции и критериях завершения.
`INTERACTIVE_STATUS.md` временно используется как инвентаризация старых примеров
и должен быть заменён автоматически проверяемым статусом в каталоге диаграмм.

## Текущее состояние

- Главная страница собрана на HTML/CSS/JavaScript без системы сборки.
- Каталог содержит 72 типа визуализаций в `chartTypes.csv`.
- Часть интерактивных примеров уже реализована на ECharts в
  `interactive-examples.js`.
- В репозитории остаются около 50 самостоятельных D3-примеров и дублирующиеся
  локальные копии D3.
- Русский текст распределён между `index.html`, `v2-data.js`,
  `chartTypes.csv` и JavaScript-конфигурациями.
- Старые каталоги с примерами являются справочным материалом до завершения
  миграции. Не удалять их массово, пока эквивалентность не подтверждена.

## Целевая структура

```text
src/
  components/
    charts/EChart.astro
    catalog/
    layout/
  content/
    charts/
      <chart-id>.json
  data/
    examples/
  i18n/
    en.ts
    ru.ts
    index.ts
  layouts/
  lib/
    charts/
      options/
      registry.ts
      types.ts
    data/
  pages/
    index.astro
    en/
      index.astro
      charts/[id].astro
    ru/
      index.astro
      charts/[id].astro
  styles/
    global.css
    tokens.css
public/
  icons/
  data/
```

Структура может уточняться в ходе миграции, но границы должны сохраняться:
контент, данные, конфигурации ECharts, UI-компоненты и переводы не смешиваются.

## Правила реализации

### Astro

- Использовать TypeScript в строгом режиме.
- По умолчанию рендерить статический HTML. Клиентский JavaScript подключать
  только для диаграмм, фильтров, диалогов и будущего импорта данных.
- Не превращать всё приложение в один клиентский компонент.
- Использовать семантические элементы, обычные ссылки и прогрессивное улучшение.
- Главная без языкового префикса должна предсказуемо вести на язык по умолчанию;
  основной контент доступен по стабильным маршрутам `/ru/` и `/en/`.

### ECharts

- ECharts — единственный runtime-движок диаграмм. D3 допустим только как
  временный источник алгоритма или для подготовки данных во время миграции.
- Импортировать только нужные модули ECharts, а не подключать CDN-сборку.
- Каждая диаграмма получает данные и локаль через явный типизированный интерфейс.
- Общие темы, оси, tooltip, легенды, состояния focus/hover и форматирование
  чисел хранятся централизованно.
- Конфигурация конкретной диаграммы не должна обращаться к DOM.
- Компонент диаграммы обязан корректно вызывать `resize`, освобождать экземпляр
  через `dispose` и учитывать `prefers-reduced-motion`.
- Для карт хранить лицензионно совместимый GeoJSON локально и явно регистрировать
  его в ECharts.
- У каждой диаграммы должны быть заголовок, краткое текстовое объяснение и
  доступная текстовая альтернатива или таблица данных.

### Контент и данные

- У каждого типа визуализации есть стабильный ASCII `id`, не зависящий от языка.
- Метаданные должны включать категорию, доступность примера, поддерживаемую
  схему данных, ограничения и тексты на RU/EN.
- Учебные данные должны быть небольшими, правдоподобными и разнообразными:
  экономика, экология, образование, городская среда, здоровье, культура и спорт.
- Не использовать реальные персональные данные.
- В примере явно указывать единицы измерения, источник/статус синтетических
  данных и смысл кодировок.
- Не подгонять один универсальный набор данных под все графики: данные должны
  раскрывать сильные и слабые стороны конкретной формы.
- Числа, даты и проценты форматировать через `Intl` для активной локали.

### Локализация

- Не размещать пользовательский текст непосредственно в компонентах или
  конфигурациях графиков.
- Русская и английская версии используют одинаковые идентификаторы и структуру.
- Любой новый пользовательский текст добавляется сразу на двух языках.
- Переключатель языка сохраняет текущую страницу или тип диаграммы.
- У страниц должны быть корректные `lang`, `hreflang`, canonical URL и
  локализованные title/description.
- Проверка сборки должна находить отсутствующие и лишние ключи перевода.

### Дизайн и доступность

- Визуальный характер: современный учебный справочник, а не маркетинговый
  лендинг и не BI-дашборд.
- Основа интерфейса — нейтральные поверхности, выразительная типографика,
  умеренные границы и цветовые акценты категорий.
- Цвет категории помогает ориентироваться, но никогда не является единственным
  носителем смысла.
- Использовать дизайн-токены для цвета, типографики, отступов, радиусов, теней и
  ширины контента. Не добавлять случайные значения в отдельных компонентах.
- Поддерживать ширины от 320 px, клавиатурную навигацию, видимый focus,
  контраст WCAG AA и масштаб текста до 200%.
- Диалоги должны удерживать фокус, закрываться по Escape, возвращать фокус
  инициатору и иметь понятное доступное имя.

## Проверки перед завершением задачи

Для каждой порции изменений:

1. Запустить форматирование, typecheck, lint и production build.
2. Проверить изменённые маршруты на русском и английском языках.
3. Проверить отсутствие ошибок в консоли и корректный resize диаграмм.
4. Проверить клавиатуру, мобильную ширину и `prefers-reduced-motion`.
5. Для новой диаграммы сравнить результат с её учебной целью, а не только со
   старым внешним видом.
6. Обновить статус миграции в `PLAN.md`; пока существует
   `INTERACTIVE_STATUS.md`, не оставлять противоречащие статусы.

Если тестовой инфраструктуры ещё нет, добавлять её в рамках соответствующего
этапа из `PLAN.md`, а до этого документировать выполненные ручные проверки.

## Работа с репозиторием

- Сохранять существующие пользовательские изменения и не переписывать
  несвязанные файлы.
- Делать небольшие тематические изменения: каркас, контентная схема, семейство
  диаграмм, локализация, дизайн или тесты.
- Не удалять старый пример, пока новый маршрут прошёл проверку и сохранены
  необходимые данные/атрибуция.
- Не коммитить сгенерированные артефакты сборки, зависимости и локальные секреты.
- При добавлении зависимости объяснять её назначение; для простой функции
  предпочитать платформенные API.

## Definition of Done для одной диаграммы

Диаграмма считается мигрированной, когда:

- она доступна по стабильному RU- и EN-маршруту;
- построена ECharts из типизированных данных без старого iframe/D3 runtime;
- содержит локализованные название, назначение, примеры и ограничения;
- адаптивна, работает с клавиатурой и имеет текстовую альтернативу;
- использует общую тему и локализованное форматирование;
- покрыта хотя бы smoke-тестом маршрута и проверкой создания конфигурации;
- старый пример больше не нужен для production-сайта.
